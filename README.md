# Osk.WolverineFx.RabbitMq.OAuth2.Patch

NuGet-библиотека для WolverineFx.RabbitMQ **6.49.0** и приложений .NET 9/10. Устанавливает два Harmony-патча автоматически при загрузке модуля приложения: после создания RabbitMQ-соединения запускает обновление OAuth2-токена, при остановке транспорта отменяет обновление и освобождает регистрацию.

```xml
<PackageReference Include="Osk.WolverineFx.RabbitMq.OAuth2.Patch" Version="6.49.0" />
```

Для установки патчей достаточно этой ссылки на пакет в запускаемом C#-проекте. Дополнительные свойства MSBuild и вызовы регистрации не нужны. Source generator внутри пакета создаёт `ModuleInitializer`, вызывающий `RabbitMqOAuth2Patches.Install()` автоматически. Повторный вызов безопасен.

`EmitCompilerGeneratedFiles` лишь сохраняет сгенерированный код на диск для просмотра; для генерации и установки патчей это свойство не требуется. В примере оно отсутствует.

Настройте `ConnectionFactory.CredentialsProvider` вашим OAuth2-провайдером, например `OAuth2ClientCredentialsProvider` из `RabbitMQ.Client.OAuth2`. Пакет использует штатный `CredentialsRefresher` версии 2.0.0, а callback передаёт новый токен открытому соединению через `IConnection.UpdateSecretAsync`. Обычные подключения с `BasicCredentialsProvider` пропускаются.

Расписанием управляет `CredentialsRefresher`: обновление выполняется сразу после регистрации, затем через 2/3 `Credentials.ValidUntil` или через 30 секунд, если срок не указан. Указанный срок должен быть положительным. Ошибки получения и отправки токена логируются; следующая попытка выполняется по расписанию штатного refresher, без собственного экспоненциального backoff. Пустые токены не отправляются, закрытые соединения пропускаются.

При остановке отменяется работа refresher и вызывается его синхронный `Dispose` в фоновом потоке. В версии 2.0.0 он ждёт задачу до пяти секунд и может выбросить исключение отмены во время задержки; адаптер обрабатывает только ожидаемую отмену и освобождает собственные подписки и ресурсы. Ограничения внутреннего `Dispose` штатной библиотеки сохраняются.

Пакет изменяет методы в процессе через Harmony. NativeAOT и trimming не поддерживаются. Генератор запускает регистрацию до кода модуля, но не перехватывает запуск произвольных процессов или уже открытые соединения. Другие версии Wolverine требуют отдельной проверки совместимости.

## Разработка

```sh
dotnet build Osk.WolverineFx.RabbitMq.OAuth2.Patch.slnx -c Release
dotnet run --project samples/StartupSmoke -c Release
dotnet test --project tests/Osk.WolverineFx.RabbitMq.OAuth2.Patch.Tests -c Release
dotnet pack src/Osk.WolverineFx.RabbitMq.OAuth2.Patch -c Release -o artifacts
bash tools/verify-package-consumer.sh
```

SDK и тестовый runner Microsoft Testing Platform закреплены в `global.json`; тесты используют TUnit. Настройки компилятора находятся в `Directory.Build.props`, версии зависимостей — в `Directory.Packages.props`. Они относятся к разработке этого репозитория. Потребителю не нужно копировать эти файлы.

Пример `samples/StartupSmoke` ссылается на проекты библиотеки и генератора, поэтому решение собирается до публикации пакета. Ссылка на генератор подключена как analyzer, чтобы проверить автоматическую установку патчей при работе с исходниками.

`tools/verify-package-consumer.sh` создаёт отдельный проект вне репозитория и подключает собранный пакет обычной ссылкой `PackageReference`. Проверка использует новый NuGet-кэш и подтверждает установку обоих патчей до `Main`.

## Интеграционные тесты

```sh
# Все семь сценариев, включая медленный тест недоступности Keycloak
dotnet test --project tests/Osk.WolverineFx.RabbitMq.OAuth2.Patch.IntegrationTests -c Release

# Шесть обычных сценариев
dotnet test --project tests/Osk.WolverineFx.RabbitMq.OAuth2.Patch.IntegrationTests -c Release --treenode-filter '/*/*/*/*[Category!=Slow]'

# Только фактическая недоступность Keycloak
dotnet test --project tests/Osk.WolverineFx.RabbitMq.OAuth2.Patch.IntegrationTests -c Release --treenode-filter '/*/*/*/*[Category=Slow]'
```

Нужны работающий локальный Docker Engine и доступ к Docker Hub и quay.io для первого скачивания образов. Testcontainers 4.16.0 сначала запускает Keycloak `26.1.4` в режиме `start-dev` по HTTP на контейнерном порту `8080`, импортирует realm и service-account client. Затем fixture запрашивает тестовый JWT и JWKS по HTTP, выбирает RSA-ключ подписи по `kid` из заголовка токена и преобразует его публичные параметры в PEM. Только после этого запускается RabbitMQ `4.1.4-management`: Testcontainers копирует публичный ключ в контейнер, а `auth_oauth2.signing_keys.<kid>` задаёт его для настоящей проверки JWT. Брокер не использует `auth_oauth2.issuer` и `auth_oauth2.jwks_url`; локальный публичный ключ заменяет получение JWKS через HTTPS.

Подпись JWT, audience, срок действия и permissions проверяет RabbitMQ. Приватный ключ генерирует и хранит Keycloak; фиксированных приватных ключей в репозитории нет. Пароли и client secret генерируются для каждого запуска. Сертификаты и CA не нужны. AMQP работает на контейнерном порту `5672`, Management API — по HTTP на `15672`. Публичные порты всех сервисов динамически назначает Docker. Контейнеры используют отдельную сеть и удаляются вместе с ней после тестов. **Эта HTTP-конфигурация предназначена только для интеграционных тестов.** Ключ копируется один раз при запуске fixture; ротация ключей Keycloak во время прогона не поддерживается.

Один комплект контейнеров и одна сеть обслуживают весь класс через hooks TUnit `Before(Class)` / `After(Class)`. Шесть обычных тестов выполняются параллельно, максимум четыре одновременно, и используют JWT со сроком жизни восемь секунд. У каждого теста собственные Wolverine host, credentials provider, очередь, имя соединения, счётчики и ожидания сообщений. Общий HTTP-клиент Management API настраивается до запуска тестов; его заголовки во время тестов не изменяются.

Тестовые host всегда включают `ValidateScopes` и `ValidateOnBuild`, независимо от окружения запуска. Scoped-сервис `IMessageBus` получается из отдельного async DI scope на каждый вызов `SendAndReceiveAsync`; scope освобождается после завершения отправки и проверки доставки.

| Тест | Проверка |
| --- | --- |
| `ConnectsWithValidToken` | Wolverine открывает два AMQP-соединения с JWT Keycloak и доставляет сообщение через RabbitMQ. |
| `RejectsInvalidToken` | Повреждение только подписи JWT при сохранении его заголовка и payload приводит к ошибке аутентификации; соединения не остаются открытыми. |
| `RefreshesExpiredToken` | После истечения исходного JWT три новых сообщения доходят до обработчика; счётчик доставки брокера увеличивается минимум на три. |
| `PreservesConnectionAfterRefresh` | После обновления и доставки сохраняются идентификаторы и время открытия обоих соединений из Management API. |
| `RecoversAfterTokenEndpointFailure` | Собственный credentials provider временно выдаёт ошибку после подключения; после регистрации ошибки и снятия отказа настоящий JWT обновляется и доставка возобновляется. |
| `StopsRefreshingAfterDispose` | Все задачи refresher завершены, запросов и обновлений в процессе нет, оба AMQP-соединения закрыты, Management API подтверждает отсутствие соединений. |
| `RecoversAfterKeycloakOutage` (`Slow`) | Keycloak приостанавливается через Docker Pause; после настоящей ошибки HTTP-запроса и Unpause обновление и доставка возобновляются. Тест выполняется эксклюзивно. |

В `RejectsInvalidToken` бюджет повторных попыток инициализации брокера равен нулю (`BrokerInitializationTimeout`): первая настоящая попытка подключения выполняется, а постоянная ошибка подписи сразу возвращается тесту. Остальные сценарии сохраняют стандартный бюджет Wolverine и автоматическое восстановление соединений.

Управляемый отказ credentials provider проверяет восстановление после ошибки провайдера. Отдельный `Slow`-сценарий проверяет недоступность настоящего HTTP endpoint и использует те же контейнеры. Оба сценария ожидают два завершённых обновления токена после снятия отказа; медленный тест дополнительно ожидает два соединения и consumer своей очереди в Management API перед отправкой. Один суммарный успешный callback не подтверждает готовность отправителя и слушателя. Pause сохраняет динамический порт; перезапуска JVM нет. Настоящие запросы токена ограничены пятью секундами; истечение этого срока преобразуется в `TimeoutException`, чтобы штатный refresher повторил запрос. Отмена при завершении работы остаётся отменой. Медленный тест не отключён и входит в запуск без фильтра.

После Dispose длительное ожидание двух TTL не требуется: задача штатного refresher ожидает получение credentials и callback с `UpdateSecretAsync`, поэтому её завершение исключает будущие попытки и незавершённые обновления. В тестах истечения JWT сохраняется ожидание фактической границы `exp` с учётом секундной точности. При проверке трёх сообщений Management API опрашивается один раз для всей группы; каждый уникальный ID отдельно ожидается в обработчике, а увеличение счётчика подтверждает доставку всей группы через брокер.

Для проверки завершения фоновых задач применяется один диагностический helper, читающий приватные задачи закреплённой версии `RabbitMQ.Client.OAuth2` 2.0.0 и соединения регистраций под блокировкой registry: публичный API не предоставляет состояния задач. При обновлении этой зависимости helper нужно проверить. Строки `[timing]` и `[integration timing]` показывают время инфраструктуры, создания/запуска/освобождения host, каждого теста и максимум одновременных тестов; подробный вывод включается через `--output Detailed`. Замеры полного прогона нужно делать после скачивания образов и отдельно от сборки. Остальные проверки используют реальные HTTP/AMQP-операции и Management API. Отсутствие Docker приводит к ошибке запуска, а не к молчаливому пропуску тестов. Холодный старт Keycloak может занять несколько минут.

Пакет пока не опубликован в NuGet. Модульные тесты используют подставные соединения; интеграционный проект использует реальные RabbitMQ и Keycloak через Testcontainers.
